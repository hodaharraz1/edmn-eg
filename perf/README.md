# اختبار الضغط (PKG-PERF-01 v3)

سكربت `k6-api.js` بيغطي المسارات الستة اللي في الخطة: التصفح، البحث (وفيه متابعة لصفحة تانية بالـcursor)، كروت/تفاصيل المنتج، تسجيل الدخول، إتمام الطلب (200 محاولة متزامنة على نفس المتغير)، ورفع إيصال.

## 1) التشغيل

```bash
# ثبّت k6: https://k6.io/docs/get-started/installation/
# شغّل السيرفر محليًا على قاعدة بيانات الاختبار، ثم:
BASE_URL=http://127.0.0.1:3000 npm run perf:k6
```

k6 بيطبع في الآخر جدول p50/p95/p99 ونسبة الأخطاء لكل مسار، والـthresholds جوه السكربت بتخلي الأمر يفشل لو الأرقام عدّت الحدود.

**ممنوع تشغيله على staging أو أي بيئة مشتركة** (docs/TESTING_POLICY.md): سيناريوهات إتمام الطلب ورفع الإيصال بتنشئ صفوفًا فعلية. محلي أو البيئة المعزولة بتاعة المالك بس.

## 2) الفيكستشرز (مطلوبة لمسارات الكتابة)

| متغير | الوصف |
|---|---|
| `TEST_EMAIL` / `TEST_PASSWORD` | عميل اختبار حالته ACTIVE وهويته APPROVED |
| `TEST_VARIANT_ID` | متغير منتج LIVE عليه مخزون |
| `TEST_ADDRESS_ID` | عنوان تابع لعميل الاختبار |
| `TEST_EXPECTED_TOTAL` | الإجمالي المتوقع بالقروش لوحدة واحدة (من صفحة المراجعة) |
| `TEST_PRODUCT_SLUG` | slug منتج LIVE (لسيناريو الكروت/التفاصيل) |

من غير المتغيرات دي سيناريوهات الكتابة بتسجل 0 محاولة (السكربت مبيختلقش حسابات لوحده) — سيناريوهات القراءة بتشتغل عادي.

## 3) قراءة النتيجة

- `checkout`: المطلوب **صفر أخطاء 5xx**. الرفود 400/409/422 (المخزون خلص / الصف ساخن) نجاح للاختبار مش فشل — المهم إن مفيش بيع زائد، وده بيتثبت بعد الجولة بـ:

```sql
select stock_on_hand, reserved from product_variants where id = '<TEST_VARIANT_ID>';
-- reserved لا يتجاوز stock_on_hand أبدًا
```

- لو `search` p95 عدّى الحد: شوف إن الفهارس موجودة (`scripts/sql/fk-indexes.sql` و`products_search_gin/trgm`) وأن صفحات التصفح بتستخدم الـcursor مش offset عميق.
