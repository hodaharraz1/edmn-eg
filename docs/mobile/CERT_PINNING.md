# تثبيت الشهادات (Certificate Pinning) — تطبيق الإدارة فقط

تطبيق الإدارة يثبّت شهادة الخادم (SEC-163): الاتصال يُرفض إذا لم تطابق الشهادة المقدَّمة بصمةً معروفة، فيُقطع
طريق أي MITM حتى لو استخدم CA مخترقًا. تطبيق العملاء لا يُثبّت (تجربة المستخدم العادي أهم، ومخاطره أقل).

## الإعداد

البصمات تُمرَّر وقت البناء (لا توجد أسرار هنا — البصمات معلومة علنية لشهادة الخادم):

```bash
--dart-define=EDMN_ADMIN_CERT_PINS=sha256/AAAA...,sha256/BBBB...
```

- البصمة هي SHA-256 لكامل شهادة الخادم (DER)، بترميز base64.
- مرّر بصمتين دائمًا: **الشهادة الحالية + الشهادة الاحتياطية/التالية**. بدون بصمة احتياطية، تدوير الشهادة يعطّل
  كل نسخ التطبيق المنشورة فورًا.
- بيئة staging وproduction لهما شهادتان مختلفتان — مرّر البصمات المناسبة لكل بناء.

## استخراج البصمة من الخادم

```bash
echo | openssl s_client -servername API.DOMAIN -connect API.DOMAIN:443 2>/dev/null \
  | openssl x509 -outform DER | openssl dgst -sha256 -binary | base64
```

## خطة التدوير

1. قبل تجديد الشهادة: أصدر الشهادة الجديدة، استخرج بصمتها، وانشر تحديث تطبيق يحمل (الحالية + الجديدة).
2. بعد وصول التحديث للمشرفين: بدّل الشهادة على الخادم.
3. في الإصدار التالي: استبدل بصمة القديمة ببصمة شهادة احتياطية جديدة.

## لم يتم التحقق في هذه البيئة

لم يُختبر الرفض الفعلي لشهادة خاطئة (يحتاج بناء التطبيق وتشغيله ضد خادم بشهادة مختلفة). الإثبات:
بناء تطبيق الإدارة ببصمة خاطئة عمدًا على staging والتأكد من فشل كل الطلبات بخطأ TLS.
